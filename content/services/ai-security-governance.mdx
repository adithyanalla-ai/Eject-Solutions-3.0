## The problem: new attack surface, old assumptions

Applications built on large language models fail in ways traditional testing never covered. The model follows instructions found in the data it reads. Natural language becomes an input channel that bypasses filters designed for code. An assistant with access to email, a database or a payment API can be talked into using it. And because outputs are probabilistic, a test that passes once may fail on the next run.

Meanwhile staff are already pasting customer data, source code and contracts into public AI tools. Without clear policy, approved options and visibility, you are accepting risk you cannot see.

## Our approach

We split the work into two connected tracks. **Technical testing** finds how your AI application can be attacked. **Governance** gives your organisation the rules, roles and evidence to use AI safely at scale. You can buy either alone, but they are most useful together.

### LLM application security testing

We threat-model the application end to end, then test against the categories in the OWASP Top 10 for LLM Applications, including:

- **Direct and indirect prompt injection**, including instructions hidden in PDFs, web pages, emails and tickets the assistant processes.
- **Sensitive information disclosure:** system prompt extraction, training or context leakage, cross-user data exposure in shared indices and caches.
- **Insecure output handling:** model output rendered as HTML or executed as code, SQL or shell commands, leading to classic injection through a new door.
- **Excessive agency:** tools and agents with broader permissions than the task needs, and missing human approval on high-impact actions.
- **Retrieval and data poisoning:** malicious or stale documents influencing answers, and access-control gaps in RAG pipelines.
- **Denial of wallet and abuse:** unbounded token use, expensive loops and missing rate limits.
- **Supply chain:** model, plugin and dependency provenance.

Testing is manual and scripted: we build attack corpora, run them repeatedly to account for variability, and record transcripts so your engineers can reproduce every finding.

### AI governance consulting

We help you build the minimum viable programme that actually gets followed: an inventory of AI tools and use cases, a risk-tiering method, an AI acceptable-use policy in plain language, data-handling rules by classification, vendor due-diligence questions, human-oversight requirements for high-impact decisions, and an incident process for AI failures. We align the structure to NIST AI RMF and, where you want a certifiable system, ISO/IEC 42001, and connect it to existing security and privacy controls rather than creating a parallel bureaucracy.

## Deliverables

1. Threat model and test plan for the AI application.
2. Findings report with attack transcripts, severity, business impact and remediation.
3. Hardening recommendations: prompt and tool design, permission scoping, output validation, retrieval filtering and monitoring.
4. A regression suite of adversarial tests you can run in CI after each change.
5. AI inventory, risk register, acceptable-use policy and vendor checklist (governance track).
6. Awareness session for staff and a technical workshop for developers.
7. Retest of fixed findings.

## Process

1. **Discovery:** architecture, data flows, models, tools, users and worst-case outcomes.
2. **Threat modelling:** map abuse cases to components and rank by impact.
3. **Testing:** manual adversarial testing plus automated attack runs.
4. **Reporting and workshop:** walk through findings with the build team.
5. **Fix and retest:** verify mitigations and leave the regression suite behind.
6. **Governance rollout:** policy, training and review cadence.

## Tools and references

We use a mix of open-source red-teaming tools, custom attack scripts and conventional application-security tooling such as Burp Suite for the web layer around the model. References include the OWASP Top 10 for LLM Applications, MITRE ATLAS for adversary techniques against AI systems, NIST AI RMF and ISO/IEC 42001. We state clearly in each report what was and was not tested, because model behaviour changes over time.
